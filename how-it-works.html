🧪 Sandboxed code execution

How code execution works without turning into chaos.

Some tasks need more than editing HTML. When the agent has to run code, it does that inside a sandboxed environment with limits, logs, and review steps. The short version: the system is here to build the requested thing, not to freeload, escape, or do something sneaky behind your back.

🛡️

What the sandbox is

Think of it like a temporary workshop. The agent gets a repo, a shell, and a bounded place to run commands needed for the task. It can inspect files, make changes, and run lightweight verification, but it does not get magical unlimited access to the world.

  • Work happens in the project workspace for this site.
  • Commands are tied to the current task, not open-ended exploration.
  • Outputs are visible through git diff, logs, and pull requests.
🚧

What keeps it contained

The agent is expected to use the smallest meaningful action, verify results, and leave an auditable trail. Riskier actions need explicit approval, and normal changes still end in a reviewable branch instead of going straight to production.

  • Scoped access: it works in this repo unless a task explicitly needs more.
  • Approval gates: destructive or sensitive actions should pause first.
  • Review gates: changes become a PR before they become the site.
Basically: yes, code can run, but it runs inside rails. The workflow is designed to be useful, inspectable, and boring in the good way.
🙋 FAQ

The reassuring version, in plain English

Is the system secretly "out to get me"?

Nope. Its job is to complete the card in front of it. It does not have its own agenda, and the process is intentionally set up around task scope, safety checks, and human review.

Can it just deploy anything it wants?

Also no. The normal path is: make the change, verify it, commit it, open a pull request, and wait for review. That is a very different vibe from "YOLO straight to prod."

What if a task needs to execute code?

Then the agent runs the command needed for that task inside the workspace and checks the result. The point is practical execution with guardrails, not unrestricted access for fun.

How would I know what happened?

You can trace the work through the Trello card, the git history, the branch, and the pull request summary. The whole setup is meant to leave breadcrumbs, not mysteries.

If you want the deepest technical explanation, the honest answer is that this setup combines scoped tools, approval rules, and repo-based review so automation stays accountable.
